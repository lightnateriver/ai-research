调研背景与筛选标准

面向 Agent / Coding 场景，推理负载从「单轮短上下文」转向「多轮、长会话、工具交错、长思考」。传统以请求为边界、LRU 一刀切的 KV Cache 管理在这一负载下出现严重的被动淘汰、重复 prefill 与 GPU 空闲。本报告只收录 2026 年发表、与 Agent 场景 KV Cache 管理直接相关、且有明确实现或实验结果的方案，按四个技术方向组织。

方向一：会话级 KV Cache 管理

3 个方案

方案 A：CacheWise — 工具感知的 Agent KV 缓存管理

vLLM 实现 arXiv 2026
发表：2026.03 场景：Coding Agent（工具调用交错） 基础：vLLM

核心问题

Agent 执行中存在大量工具调用，工具执行期间（读文件、跑测试、等用户）GPU 上该会话的 KV Cache 被 LRU 被动淘汰，恢复时需要昂贵的重新 prefill。现有系统不区分「马上回来的工具等待」与「真正结束的请求」。

实现流程

  • 工具元数据预测（τ 估计）：根据工具调用类型与历史，预测该会话下一次访问的间隔时间 τ。
  • Prefix-aware 调度：调度器感知请求间的 prefix 复用关系，把同一会话/相近 prefix 的请求聚拢。
  • 间隔感知保留：对预测 τ 较小（快速返回）的会话优先保留 KV，对长间隔会话降级到 CPU。
效果：KV 淘汰量降低 2~2.6 倍，端到端会话完成时间最高改善 3.5 倍。
局限：依赖工具类型可观测；τ 预测对全新工具或高方差任务不够准；只解决「保留在哪」，不解决会话持久化与 block 级差异化。

方案 B：CacheScout — 在线马尔可夫预测 + Survival 淘汰 + Warmup 预取

vLLM 实现 arXiv 2026
发表：2026.05 场景：多会话 Agent serving 基础：vLLM

核心问题

LRU 只看「最近是否使用」，不看「接下来谁会被用到」。Agent 会话的 cache 块访问遵循可学习的转移规律，但现有淘汰策略完全忽略这一统计结构，也不会在会话恢复前主动预热。

实现流程

  • 在线马尔可夫转换学习：在线维护 cache 块/会话状态间的转移概率矩阵，随执行实时更新，无需离线训练。
  • Survival 淘汰策略：基于「未来被访问概率」（生存概率）而非 recency 决定淘汰谁，优先驱逐预计不再使用的块。
  • Warmup 预取：当预测某会话即将恢复时，在其真正到达前把 KV 从 CPU 预热回 GPU。
效果：命中率提升 10~18pp，TTFT 降低 18%~45%。
局限：预测粒度在会话/块级但不区分上下文类型（system / scratchpad）；马尔可夫一阶假设对长程依赖刻画有限；无跨重启持久化。

方案 C：UNISON — Near-Memory 事件驱动的 KV 调度（Spear + Tide）

硬件协同 arXiv 2026
发表：2026.06 场景：高并发 Agent + 近内存处理

核心问题

软件层周期性轮询 KV 状态、再做批量决策，引入延迟且无法在访问发生的瞬间响应。UNISON 主张把 KV 调度下沉到 near-memory，用事件驱动方式在块被访问/释放的当下即时更新优先级。

实现流程

  • Spear（ ranking 引擎）：近内存硬件单元维护块的 ranking score，访问事件触发即时更新。
  • Tide（数据搬运引擎）：依据 ranking 在 GPU/CPU/存储层间异步搬运 KV，与计算重叠。
  • 共享 ranking：淘汰与提升共用同一套实时 score，避免软件层策略不一致。
特点：事件驱动 + 近内存计算，消除软件轮询延迟，淘汰与提升策略统一。
局限：依赖专用/近内存硬件，纯软件栈（vLLM/llm-d）无法直接落地；工程门槛高，更适合作为长期架构参考。

方向二：Typed Retention 差异化保留

3 个方案

方案 D：MemDecay — 区域感知的差异化衰减与 Critical Pin

Training-free arXiv 2026
发表：2026.04 场景：Agent 异构上下文（system / scratchpad / 用户）

核心问题

Agent 上下文中不同区域的复用价值差异巨大：system prompt、工具定义几乎每步都复用；scratchpad/临时思考半衰期极短。LRU/LFU 对所有 token 一视同仁，导致高价值 system 区域被低价值临时 token 挤出。

实现流程

  • 区域划分：把上下文划分为 system / instruction / user / scratchpad / tool-result 等区域。
  • 区域特定 base priority + decay：每个区域有不同的初始优先级和衰减速率——system 区域高基线、慢衰减；scratchpad 低基线、快衰减。
  • Critical region pin：对关键区域（system prompt、常驻工具定义）直接 pin 住，永不淘汰。
效果：关键 system 区域在全部 24 个测试场景中完整保留，无需训练。
局限：区域边界依赖引擎能识别 token 类型（需要框架/协议配合标注）；衰减参数需按负载标定；不解决预取与持久化。

方案 E：KVLearn — 学习型复用预测（PRP）与成本感知保留分（CARS）

分解式服务 arXiv 2026
发表：2026.05 场景：PD 分离 / 分解式推理

核心问题

在分解式（prefill/decode 分离、多层缓存）架构中，保留一个 KV 块的成本（占用 HBM、网络传输）差异很大，而复用收益也不同。简单的「会不会复用」二元预测无法指导跨层保留决策。

实现流程

  • PRP（Probabilistic Reuse Prediction）：学习模型输出每个块未来被复用的概率，而非二值判断。
  • CARS（Cost-Aware Retention Score）：保留分 = 复用概率 × 复用收益 − 保留成本（HBM 占用 / 传输代价），按分数决定块放在哪一层。
  • 跨层联合决策：在 GPU / CPU / 远端存储间做成本-收益最优的放置。
特点：从「会不会复用」升级到「保留是否划算」，把保留决策建模为期望收益优化，适配多层与 PD 分离。
局限：需要训练/在线学习预测器，引入冷启动与泛化问题；成本模型参数依赖具体硬件与网络。

方案 F：Not All Thoughts Need HBM — 累积注意力分层与零误差 DDR 预取

语义分层 arXiv 2026
发表：2026.06 场景：长思考（long-CoT）Agent

核心问题

长思考 Agent 产生海量 reasoning/scratchpad token，但注意力分析显示：越往后的思考，越只关注最近的少量思考步和早期的少量关键结论。大量中间思考 token 的 KV 其实不需要常驻 HBM。

实现流程

  • 累积注意力分析：统计每个 token 在后续所有步中累积获得的注意力分数，识别「真正被反复关注」的少数关键 token。
  • 四级分层：按累积注意力把 KV 分为 4 级——关键结论常驻 HBM，低关注思考降级到 CPU/DDR。
  • 零误差 DDR 预取：当注意力确实需要降级的 token 时，从 DDR 精确预取回 HBM，保证输出与全量驻留完全一致（零精度损失）。
特点：基于真实注意力证据做语义级分层，HBM 只留高价值 KV，配合零误差按需预取，精度无损地释放显存。
局限：需要访问注意力权重（部分引擎不暴露）；在线统计有开销；分层与预取逻辑侵入 attention 内核。

方向三：主动预取与预测

2 个方案

方案 G：Prediction-based KV Cache Prefetching（HiCache 之上）

SGLang HiCache arXiv:2605.06472
发表：2026.05 场景：动态 Agent 工作流 基础：SGLang HiCache 基础设施

核心问题

动态 agent 工作流中，KV cache 节点的未来复用是可预测的（基于执行历史），但现有系统被动等待 cache miss 后才从 CPU 加载。可以利用预测在 miss 发生前主动加载，将传输延迟隐藏在 ongoing decode 步骤之后。

实现流程

  • 复用预测器：基于 agent 执行历史和工作流结构，预测哪些 cache 节点近期会被复用。
  • 保守预取（Conservative Prefetching）：核心权衡——用「已知有价值的 GPU 缓存」交换「推测有价值的 host 缓存」。只有当预测置信度足够高、且 GPU 有空闲空间时才预取。
  • 利用 HiCache：基于 SGLang 的 HiCache 三层架构（GPU/CPU/外部存储），预取操作从 CPU → GPU 异步执行，不阻塞 decode。
特点：基于 SGLang HiCache 实现，保守预取策略避免错误预取浪费资源，将 CPU→GPU 传输延迟隐藏在 decode 之后。
局限：预测器准确率直接决定收益；GPU 空间紧张时预取无法执行；预取和正常请求竞争 PCIe 带宽。

方案 H：Predictive Multi-Tier Memory Management

多层预测 arXiv:2604.26968
发表：2026.04 场景：大规模 GPU 推理多层 KV 管理

核心问题

多层 KV 缓存（GPU/CPU/SSD）中，现有 LRU 策略不考虑注意力的位置局部性。早期层倾向局部注意力（只需附近 token），后期层倾向全局注意力（需要所有历史 token）。统一的预取窗口效率低。

实现流程

  • 位置感知预取：监控当前 decode 步的位置范围，对覆盖 [n, n+w] 位置的 block 发异步提升请求（从低层 → GPU）。
  • 自适应窗口：窗口 w 根据观察到的注意力模式自适应——局部注意力层用窄窗口，全局注意力层用宽窗口。
  • 贝叶斯复用预测：结合贝叶斯方法预测 block 复用概率，与位置感知结合做预取决策。
  • RoPE-aware：考虑旋转位置编码的特性，优化预取的 block 选择。
效果：相比 LRU，RoPE-aware 预取将 cache miss 率降低 25%。
局限：更偏通用多层内存管理，不是专门针对 agent 场景；需要在线监控注意力模式，增加了调度复杂度。

方向四：会话持久化与 Snapshot

3 个方案

方案 I：Agent Memory

Edge 多 Agent arXiv:2603.04428
发表：2026.03 场景：边缘设备多 Agent 持久化 KV

核心问题

边缘设备上运行多 agent 系统时，GPU 内存有限，agent 切换时 KV 被淘汰，恢复需要完整重 prefill（4K context 需 15.7 秒）。如果将 KV 持久化到磁盘，恢复时直接加载而非重算，可以大幅降低切换延迟。

实现流程

  • Q4 量化持久化：每个 agent 的 KV cache 以 4-bit 量化格式写入磁盘，体积压缩 4×。
  • 直接缓存恢复：agent 切换回来时，从磁盘加载 Q4 KV 直接注入 attention 层，跳过 O(n) 的 prefill 计算。
  • 交错隐藏延迟：多 agent 系统天然交错——一个 agent 生成时，下一个 agent 加载 KV，加载延迟被隐藏。
  • 跨重启持久化：服务器完整重启后，agent 的 KV cache 仍在磁盘上，TTFT 保持暖缓存水平。
效果：消除 agent 切换时的完整重 prefill（4K context 从 15.7 秒降至磁盘加载时间），支持跨服务器重启持久化。
局限：针对边缘设备场景，Q4 量化可能影响精度；需要文件系统管理多 agent 的 KV 文件；未涉及分布式场景。

方案 J：MorphCloud-LLM

云原生 Checkpoint MDPI 2026
发表：2026.08 场景：Spot 实例弹性服务 + 抢占恢复

核心问题

云环境中使用 spot 实例降低成本，但实例可能被随时抢占。现有服务在抢占后丢失所有 KV cache 状态，恢复需要从头开始。需要轻量级的增量 KV checkpoint 机制，支持亚秒级恢复。

实现流程

  • 异步增量 Checkpoint：流式 KV-cache 机制，持续将增量推理状态同步到分解式持久存储（S3 / GCS），吞吐开销 < 3%。
  • 亚秒级恢复：替换实例上，从持久存储恢复 KV cache（最大 32 GB），端到端迁移延迟 1390 ms（含检测+状态传输+恢复）。
  • 推测解码连续性：恢复后保持 speculative decoding 的状态连续性，不需要重新预热。
  • 透明抢占恢复：对上层应用透明，spot 实例被回收时自动迁移到新实例。
效果：异步 checkpoint 吞吐开销 < 3%，最大 32 GB KV 的端到端恢复延迟 1390 ms，支持 speculative decoding 连续性。
局限：依赖云对象存储（S3/GCS），本地部署需替代方案；恢复延迟受网络带宽影响；主要为容错设计，非专门针对 agent 会话管理。

方案 K：CacheFlow

3D 并行恢复 arXiv:2604.25080
发表：2026.04 场景：KV cache 恢复的多维并行加速

核心问题

KV cache 恢复（从存储/远端加载后重建）通常是串行的：先 I/O 再计算，或者只沿一个维度并行。Transformer 推理的结构依赖关系允许沿 token、层、GPU 三个维度同时并行，但现有系统没有利用。

实现流程

  • 3D 并行抽象：将 KV cache 恢复建模为跨 token、层、GPU 三个维度的并行执行问题，统一抽象覆盖 recomputation 和 I/O。
  • 细粒度重叠：沿 transformer 结构依赖关系，细粒度地重叠计算和 I/O——某层的 KV 从存储加载时，另一层可以同时 recompute。
  • Batch-aware 双指针调度器：跨请求联合优化计算和 I/O 分配，优先执行边际减少最多的操作。
特点：将 KV 恢复从串行提升为 token/layer/GPU 三维并行，配合 batch-aware 调度器最大化 I/O 与计算重叠。
局限：需要多 GPU 环境才能发挥 GPU 维并行；调度器复杂度较高；论文侧重恢复速度优化，不涉及持久化存储格式设计。

对你方案的启示

  1. CacheScout 是最接近的现有工作——已在 vLLM 上实现了 agent 感知的 eviction + prefetch，但它只做了 agent 级别的马尔可夫预测，没有做 block 级别的 typed retention，也没有会话持久化。你的方案可以在其基础上增加 typed retention（参考 MemDecay）和会话持久化（参考 Agent Memory + MorphCloud）。
  2. Typed retention 已有 MemDecay 的 training-free 方案——区域划分 + 区域特定 decay + pin，实现简单且效果明确。可以直接借鉴其区域参数化设计。
  3. 会话持久化有两条路径——Agent Memory 的 Q4 直接注入（适合边缘/单节点）和 MorphCloud 的增量 checkpoint（适合云原生/分布式）。你的方案可以根据部署场景选择或组合。
  4. 预取策略需要保守——Prediction-based KV 的「高置信度 + 空闲空间」双条件原则值得遵循，避免错误预取浪费资源。
  5. 所有现有方案都是单点优化——没有一个方案同时整合会话级管理 + typed retention + 持久化 + 预取。你的差异化在于做一个统一的会话级 KB 管理层，整合这些机制。

评估会话级 KV Cache 管理策略需要真实的 agent 执行 trace。以下是 2026 年可用的开源数据集，按对 KV cache 研究的相关性排序。

数据集 1：TraceLab（首推）

专为 Serving 设计 GitHub arXiv:2606.30560
发布：2026.06 机构：华盛顿大学 SyFI Lab 规模：~4,300 会话 / 35 万 LLM steps / 43 万 tool calls

数据来源

43 名开发者在 8 个月内日常使用 Claude Code 和 Codex 的真实日志，覆盖 20+ 模型版本。采集流水线自动提取、标准化格式、匿名化处理。

数据格式

  • 统一 step-level schema：每行 = 一次 LLM 调用 + 其产生的 tool calls
  • 事件类型：metadata / user message / reasoning / output / tool call / tool result，每个事件带时间戳
  • Token 统计：每次 LLM 调用报告 input/output token usage
  • 会话级统计：平均 9.2 requests/session，平均 73.6 tool-initiated steps，p99 达 1,107 steps

对 KV Cache 研究的价值

  • 论文直接分析了 prefix cache 行为：总体命中率 95.7%，但 user-initiated step 仅 84.4%（人思考时间长导致 eviction）
  • idle >5 分钟开始出现 cache miss，>1 小时几乎全 miss——可直接用于模拟不同 eviction 策略的效果
  • prefill amplification factor 5.3×（实际 prefill 是理想缓存的 5.3 倍），量化了优化空间
  • 可重放 trace 对比不同 KV 管理策略（LRU / predictive / typed retention）
推荐用途：会话级 KV 管理策略的主要评估数据集，格式最对口，有真实时间间隔可模拟 eviction 和 prefetch。

数据集 2：SWE-chat

真实在野数据 arXiv:2604.20779
发布：2026.04 规模：6,000 会话 / 6.3 万 user prompts / 35.5 万 tool calls / 270 万事件

数据来源

通过 Entire.io 开源 CLI 从 200+ 公开 GitHub 仓库自动收集，开发者主动 opt-in。支持 Claude Code、OpenCode、Gemini CLI、Cursor、Factory AI Droid。

数据特点

  • "Living dataset"：采集流水线持续自动发现和处理新会话，数据不断增长
  • 代码作者归属：每行代码标注是人写还是 agent 写，可分析 agent 产出的实际留存率
  • Tool 类型丰富：read(19.8%)、edit(19.6%)、git/gh(11.9%)、grep(10.1%)、bash:build(8.0%) 等 12 类
  • 用户行为真实：44% 的 turn 中用户会纠正/中断 agent，41% 会话是"vibe coding"（agent 写几乎所有代码）

对 KV Cache 研究的价值

更偏代码质量分析，但 trace 完整（含 user prompts、agent responses、tool calls、token usage），可用于推理负载模拟。优势是用户多样性高（200+ 仓库），能补充 TraceLab 仅 43 名开发者的样本偏差。

局限：不是专门为推理系统设计，缺少标准化的 step-level 时间戳格式；更适合做负载特征分析而非精确的 KV 策略对比。

数据集 3：GAIATrace + Vidur-Agent

Token-Level + 模拟器 arXiv:2606.01725
发布：2026.06 场景：通用任务 Agent（非 Coding） 规模：268 任务 / 7,488 LLM queries

数据来源

两个 SOTA agent 系统——MiroThinker（103 任务）和 OWL（165 任务）——运行 GAIA benchmark 的完整 trace。使用开源 LLM（gpt-oss-120b / MiroThinker-1.7-mini）作为主模型以捕获完整 reasoning tokens。

数据特点

  • 第一个 token-level trace：捕获完整 reasoning tokens（MiroThinker reasoning token ratio 70.3%），而非仅 input/output 统计
  • Task-level 结构：每个高层 task 包含有序的多轮 LLM queries 和 tool calls
  • 多模型 trace：同时记录 Main-LLM 和 Sub-LLM（gpt-4o / gpt-4o-mini）的调用
  • 配套 Vidur-Agent 模拟器：支持 KV cache、prefix cache、PD 分解、异构模型、调度策略的 trace-driven 仿真

对 KV Cache 研究的价值

  • 报告了 KV hit rate：intra-task 58–79%，inter-task 59–80%——比 coding agent 低很多，因为通用任务的上下文复用模式不同
  • Vidur-Agent 可快速仿真不同 KV 策略，无需真实 GPU 集群
  • trace 可直接在 vLLM 上重放（vLLM 支持 custom trace benchmark）
局限：是通用任务 agent 不是 coding agent，工具调用模式和上下文增长规律不同；任务量较小（268 个）。

数据集 4：LMCache Claude Code Traces

KV Cache 专用 LMCache Blog
发布：2026.05 规模：739 个匿名化 Claude Code 对话 trace

数据特点

LMCache 团队用于多轮 agentic workload 的 KV cache benchmark，直接对比了三种策略：no cache、vLLM HBM prefix cache、LMCache。在 MiniMax-M2.5（230GB FP8 MoE）+ 2× AMD MI300X + vLLM 0.19.0 上测试。

对 KV Cache 研究的价值

量小但专门为 KV cache 评估设计，trace 格式可直接用于 vLLM + LMCache 的 benchmark pipeline。适合做快速的概念验证（PoC）评估。

局限：仅 739 个会话，规模有限；未完全公开为独立数据集（嵌入在 LMCache benchmark 中）。

数据集 5：Open-SWE-Traces

大规模训练轨迹 arXiv:2606.16038
发布：2026.06 规模：207,489 trajectories / 9 种语言 / 20,000 PR

数据来源

从 20,000 个真实世界 PR 中，通过 OpenHands 和 SWE-agent harness 生成的 agent trajectories。使用 Minimax-M2.5 生成带显式 thinking 过程的轨迹。覆盖 Python、Go、TS、JS、Rust、Java、PHP、C、C++ 九种语言。

对 KV Cache 研究的价值

规模最大（20 万+），语言多样性好。但主要用于模型蒸馏/训练，缺少时间戳和 token 级细节，不适合精确的推理系统评估。可用于分析 agent 行为模式（工具调用序列、上下文长度分布）。

局限：是合成轨迹（用 agent harness 跑 PR 生成），不是真实用户日常使用；缺少推理时间间隔，无法模拟 eviction 行为。

选型建议

  1. 主评估集：TraceLab——格式专为 serving 设计，有精确时间戳和 token 统计，可直接重放对比不同 KV 策略。
  2. 快速仿真：GAIATrace + Vidur-Agent——无需 GPU 集群即可在模拟器中验证策略趋势，适合早期原型迭代。
  3. 补充多样性：SWE-chat——用户和仓库多样性高，可验证策略在更广泛分布上的鲁棒性。
  4. 注意缺口：目前没有任何数据集包含 KV cache block 级别的访问 trace（即每个 block 何时被命中/淘汰），所有数据集都需要在推理引擎中重放后才能采集这类信号。这是你做研究时需要自己搭建的 measurement pipeline。
